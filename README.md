# Reef Point Seg (`reef_point_seg`)

Reef Point Seg, display name VEGA, turns decades of TCRMP CVR coral point-count data into a trained YOLO11 instance-segmentation model, for the TCRMP benthic-monitoring team, and trains a YOLO11 detector from a bounding-box dataset staged on its Bounding Boxes page. A project belongs to one of those two families and its window shows only that family's stages. This README is the technical contract; the procedure a student follows, stage by stage with the annotator's keys, is the manual at `/mnt/rip/vicarius_drive/vicarius/_DOCS/modules/reef_point_seg.md` (the Manual button on the module page).

## What it does and why it exists

Reef Point Seg is a launcher-style VICARIUS pipeline that converts the point-count records the TCRMP program has collected for decades into pixel-level coral masks and, from those masks, a trained segmentation model. TCRMP surveys record benthos as CoralNet-style point annotations: a survey photo, a grid of labelled points, and a species code at each point. That format records what sits under each point, and it leaves the colony location and outline undefined. Reef Point Seg supplies the colony outline. It reads the point labels, verifies each point against the survey image, segments the object under each point with SAM3, and assembles the accepted masks into a YOLO11-segmentation training set. Steps 6 through 8 then train, evaluate, and run the model.

The module solves a labelling-cost problem. Drawing coral outlines by hand across every TCRMP site, transect, and year would cost more labor than the project can spend. The existing point labels already carry an established species identity at a known pixel, so the pipeline uses each point as a SAM3 click prompt and lets the segmenter propose the outline. A human reviewer then accepts, edits, or discards each proposed mask before it enters training data. The reviewer could flag uncertain corals REVIEW, and the module shipped them to an outside taxonomic expert through a GitHub-Pages viewer, who returned identifications the operator folded back in for later projects to reuse. Setting a new REVIEW flag is suspended since 2026-09-06 and so is publishing to that viewer; see "Expert-review flagging is suspended" below. Masks flagged before that date keep their flags, and importing an expert identification still works.

The operator runs Reef Point Seg as an orchestrated, resumable project. Each project is a directory on disk that records the exact step, configuration, and outputs, so a run can stop after any step and resume later with its state restored. One person drives the whole flow through a browser: the orchestrator serves a single sidebar UI and folds each sub-tool behind it, so the operator never sees a sub-app startup form.

## Where it sits in the pipeline

Reef Point Seg is the head of its own chain, separate from the 3D photogrammetry survey chain. The inputs come from the TCRMP program and from a legacy point-index tool, and no other VICARIUS module feeds them:

- The TCRMP CVR Excel workbooks (`tcrmp_cvr`) are the raw point-count exports the monitoring program produces.
- The TCRMP clip frames (`tcrmp_clip`) are the survey still frames sampled from transect video.
- The `cpc_all` index is a static pre-2020 CPCe point store built once by the legacy `TCRMPclip_cpcID` tool.

Downstream, the module produces a trained YOLO11-segmentation checkpoint (`best.pt`) plus evaluation and inference artifacts. Within this repo, no VICARIUS module automatically consumes those outputs; the trained model and its per-image detections are the handoff artifacts for later coral-cover and demography analysis. Any automatic downstream wiring beyond this repo is unverified here.

## Parameters

The first five rows are the operator-facing parameters declared in `module.yaml`. Each also has a per-step default in `config/pipeline.yaml` and a per-project value saved into `project.json`; the project value takes precedence at run time. The last two rows are Step 3 site-balance controls that live in the orchestrator panel and `project.json` only, not in `module.yaml`. The Step 5 Train Model panel can import a preset from `config/presets/` that replaces the epochs, image size, batch and augmentation values; the panel shows the values that will run.

| Parameter | Type | Default | What it controls |
|-----------|------|---------|------------------|
| `target_species` | string | `OFRA, PA, OA, OFAV, AL, MC, AA` | Priority species codes for balanced selection in Step 3 and review filtering in Step 4. The live Step 3 picker opens with nothing preselected (the `config/pipeline.yaml` default is empty), so the operator chooses target labels for each project. |
| `target_instances_per_species` | integer | 1000 | Minimum count of point-labels per target species that Step 3 collects before selection stops. |
| `epochs` | integer | 500 | Maximum training epochs for Step 6. |
| `imgsz` | integer | 512 | Training, evaluation, and inference image size, in pixels on a side. |
| `model` | string | `yolo11m-seg.pt` | Base model: one of the YOLO11 checkpoints Ultralytics trained on COCO, a set of everyday photographs (`yolo11{n,s,m,l,x}-seg.pt` for the Segmentation task, `yolo11{n,s,m,l,x}.pt` for the Detector task). | `site_balance` | boolean | on | Whether Step 3 spreads the selection across TCRMP sites as well as across years. The Step 3 panel shows it as the "Balance across sites" checkbox; unticking it passes `--no-site-balance` to `scripts/TCRMPcvr_chooseImages/src/select_images.py`. |

## How it works inside

The entry script `run_pipeline.py` inserts `scripts/pipeline_orchestrator/` on the path and calls `create_app()` from `app.py`, which builds a Flask application and serves it on port 5050 (`app.run(host=0.0.0.0, port=5050)`). The orchestrator is the single UI; it launches each sub-tool as a child process on its own port and proxies or mounts it behind port 5050.

`config/pipeline.yaml` is the source of truth for paths, ports, interpreters, and per-step defaults. It defines the eight internal step entry points, all run with the unified environment Python at `env/bin/python`. The rail numbers are display numbers and differ from the internal step keys. On a segmentation project display 4 is the combined annotator (internal route key `step4test`, output directory `step4test_combinedAnnotate/`, beside the routing pass in `step4_routeChosenImages/`), because the legacy separate Place Points and Segment tiles were replaced by one annotator; display 5, 6 and 7 are internal steps 6, 7 and 8 (`step6_trainModel/`, `step7_evaluateModel/`, `step8_inference/`). On a detection project the same three internal steps are displayed as 1, 2 and 3, since the annotation stages are not on its rail. Internal step keys and output directory names never change (`step1_*` through `step8_*`, `step4test_combinedAnnotate`); only the display numbers do, and no internal key or directory token is rendered on screen.

1. Step 1, `TCRMPcvr_makeAllPoints/run.py`: parses every CVR workbook into `all_points.csv` and the master-codes table.
2. Step 2, `TCRMPcvr_recodeSpecies/src/app.py` (sub-app port 5055, or a headless `remap_loader`): applies rename, merge, and exclude rules and writes the recoded points plus `remap_log.json`.
3. Step 3, `TCRMPcvr_chooseImages/src/select_images.py`: runs the greedy, fresh-random frame selection gated on image and point-source eligibility, balanced across years and (since 1.6.0) across sites, and writes `selected_frames.csv`, the route splits, `reserve_frames.csv`, `selection_summary.txt`, and `selection_summary.json`. See "Site balancing in Step 3" below.
4. Step 4 routing, `TCRMPclip_placePoints/src/app.py` (sub-app port 5065): resolves the points of each selected frame from CPC coordinates (pre-2020) or OCR (2020 and later) and writes the per-year `sam_click_prompts.json` into `routed_input/`.
5. Place + Segment, `TCRMPclip_combinedAnnotate/src/app.py` (sub-app port 5080): the combined annotator that folds legacy point placement and segmentation into one pass. The operator arms a species, clicks, and SAM3 segments the object under the click; the operator accepts, edits, or scraps each mask. It reads `routed_input/` as a read-only reference layer, writes the YOLO bundle and `export_manifest.csv` under `step4test_combinedAnnotate/`, and pushed REVIEW-flagged masks to the expert-review repo until that was suspended on 2026-09-06 (the export route now returns a count of the masks it skipped and publishes nothing). The review topbar's Import Images control (`POST /api/import_images`, `src/custom_imports.py`) also accepts operator-supplied images from outside the pipeline: each file is copied verbatim into `step4test_combinedAnnotate/custom_imports/originals/`, delivered into `custom_imports/raw/` (downscaled to the 1920px lores standard when oversized, the same rule as routed frames, with the scale recorded in `custom_imports/imports_manifest.json`), added to the review queue with a Custom badge, logged in the run's `project.json` (`access_log` + `custom_imports`), and exported through the normal batch-export path like any routed frame.
6. Step 6, `TCRMPtrain_oceankindCV/run_step6.sh`: splits the training source into train, valid, and test and trains YOLO11 (Ultralytics) as a segmenter or a detector according to the Training task, writing `runs/{run_name}/weights/best.pt`. An outline export is split by `src/pinned_split.py` (frozen transect holdout); a staged box dataset is split by `src/detect_dataset.py`, which replays the dataset's own `split_pins.json` when it carries one (holdout mode `staged`, so a retrain holds out the images the dataset's original experiment held out) and otherwise draws a split seeded on the dataset name with the panel's validation and test fractions (holdout mode `lab-random`). Both write `dataset/split_manifest.json` with the seed, the fractions, per-split counts and a split fingerprint. The orchestrator refuses a second Start Training with HTTP 409 while a run is live, before any file is written, and names a trainer that outlived an orchestrator restart.
7. Step 7, `TCRMPtrain_oceankindCV/src/evaluate_run.py`: runs one Ultralytics `val()` pass and writes `metrics.json`, `report.md`, `report.html`, `report.pdf` (printed from `report.html` by headless Chrome at `/usr/bin/google-chrome`, or the binary named by `TCRMP_CHROME_BINARY`), `previews/` and `val_run/`, then appends the run's row to the rounds ledger. Per-species rows are mapped through the validator's class index (`ap_class_index`), so a species absent from the split is listed as absent rather than shifting every later row. The script exits 0 when every requested output exists, 2 when `metrics.json` and `report.md` were written but the PDF, the ledger row or the export copy was not (the console names which), and 1 on any other error; the orchestrator marks a non-zero exit as a failed step.
8. Step 8, `TCRMPtrain_oceankindCV/src/run_inference.py`: runs `best.pt` over a chosen image source on the chosen device and writes `manifest.json`, `overlays/` (when `--save_overlays` is set: every instance filled at the fill opacity, outlined, and labelled with a chip reading the species in full plus its confidence, kept inside the frame) and `predictions.json` (when `--save_predictions` is set). `--codes_csv` (the orchestrator passes the master codes table) resolves a class named by a bare code to its full name.

## Site balancing in Step 3

Step 3 used to balance the frame selection across years only, which let a handful of well-sampled sites dominate a training set. Since 1.6.0 it balances across years and across TCRMP sites.

- **Controls.** The Step 3 panel carries a "Balance across sites" checkbox (on by default) and a "Max share per site" number (default 0.25, meaning no single site may hold more than 25 percent of the selected frames). The orchestrator clamps the posted share into (0, 1] before passing `--max-site-frac`; unticking the checkbox passes `--no-site-balance` and restores the year-only behavior.
- **Allocator.** `site_balanced_select` in `scripts/TCRMPcvr_chooseImages/src/select_images.py` allocates a per-site quota per label, gives every site an inclusion floor of one frame, then fills greedily. Two real bugs were fixed while adding it: a deadlock where a project with fewer sites than the cap allows could never reach its target, and crosstalk where a top-up for one species consumed another species' allocation.
- **Honest shortfalls.** When a label misses its target the summary now names the cause instead of always printing "pool exhausted": `cap-limited` (the pool could have supplied the target but the per-site cap held it back), `allocation-limited` (the allocation covered the target but the per-site pools did not), or `pool exhausted` (the eligible pool really is that small). Projects with only two or three sites now reach full targets at roughly a 35 to 50 percent maximum site share, where the old code returned one frame per site.
- **Reporting.** `selection_summary.json` records per-site and per-species achieved counts, the cap in force, and the shortfall reason per label. The Step 3 panel renders it as a Sites table with a cap line.
- **Refill.** Step 4's OCR-failure refill is site-aware: when a 2020-and-later frame yields no points, the replacement is drawn from the reserve pool at the site furthest behind its allocation rather than whichever reserve happens to rank lowest. The routing report records `refill_site` and `site_counts_after` so the post-refill balance is visible.

## Refine loop (model-assisted labeling)

Steps 1 through 8 take a project from raw point counts to a trained, evaluated, inference-ready model once. The Refine loop is what closes that into a repeatable cycle: run inference, let the model propose masks on new frames, have a human correct only what the model got wrong, and retrain on the corrected set. Version 1.2.0 adds the machinery for this loop; the plan is `docs/superpowers/plans/2026-07-09-reefpointseg-model-assist-loop.md`.

**The loop path.** Step 3 (Choose Images) selects a fresh batch of frames. Step 4 (Place + Segment) is where a human labels them from scratch the first time. Train (Step 5/6) fits a model on the labeled set. Evaluate (Step 6/7) scores it and appends a row to the rounds ledger (`rounds.csv`). Infer (Step 7/8) runs the trained model over a new batch of frames and, with `--save_predictions`, writes `predictions.json`, a machine-readable list of per-detection class, confidence, and geometry (a polygon for a segmenter, a box for a detector). Refine reopens Step 4 in loop mode: `seed_from_predictions.py` reads `predictions.json` and seeds each above-threshold detection into the combined annotator as a pending, `source_type: model` mask, so the operator reviews and corrects model output instead of drawing every mask by hand. The seeder reads polygon entries only; a detector's box-only entries are skipped (a box-to-polygon fallback is an open follow-up). The corrected labels flow back into Train (Step 5/6), and the cycle repeats:

```
3 (Choose Images) -> 4 (Place + Segment) -> Train 5 -> Evaluate 6 -> Infer 7
                                                 ^                      |
                                                 |                      v
                                        Train 5 <- Refine (Step 4, loop mode)
```

**Two retrain strategies.** Once a Refine round has corrected labels, the operator chooses how the next training run starts:

- **Train a new model** trains from a base model (the default state of the Train panel) over the full merged labelset (original labels plus every accepted Refine correction). Slower, because it trains from scratch, but it never inherits a bias from an earlier round and gives the cleanest apples-to-apples comparison in the rounds ledger.
- **Continue from the champion** is fast. It starts from the current champion's `best.pt` under the "Continue from a VEGA model (advanced)" disclosure instead of a base model, with the learning rate lowered to 0.001 and the first 10 layers frozen, so the run adapts to the new corrections without unlearning what the champion already does well. Use it for quick iteration between labeling sessions; fall back to training a new model periodically, or whenever the labelset has grown enough that a from-scratch fit is worth the wall time, or if continuing from the champion starts trending down on the gates below. The Refine panel's after-export card carries two buttons, "Train a new model" and "Continue from the champion", that open Train Model with the disclosure cleared or opened with the champion chosen; when no champion of this task has been promoted yet, "Continue from the champion" says so instead of opening a run with nothing chosen.

**Frozen transect holdout.** Every round needs to be judged against the same yardstick, so the validation and test splits are frozen by transect rather than re-randomized on every training run: transect 5 is always validation, transect 6 is always test, and transects 1 through 4 always go to train (`dataset/split_manifest.json`, `holdout_mode: "transect"`). Since 2026-09-04 the manifest (schema 2) also records the seed the run carried (the Step 5 panel passes no seed, so it is always 1), the validation and test fractions, per-split counts and a split fingerprint (SHA-256 over the sorted image-to-split assignment, first 16 hex characters, scheme `sha256-16/netstring-utf8-sorted-v1`), written the same way by both splitters. This keeps video-adjacent frames from splitting across train and holdout, which would otherwise inflate the reported mAP, and it means a round-over-round metric comparison is actually comparable. If a project has no labeled frames yet on the val or test transect, the split does not hard-fail: it gracefully degrades to a seeded random holdout for that project (`holdout_mode: "transect-degraded"`, with a `degrade_warning` naming the empty transect) and self-heals back to the clean transect split the moment both holdout transects have labeled frames. **Never seed a holdout transect.** The Refine seeder is fail-closed on this: it requires `split_manifest.json` to exist and excludes any frame pinned to valid/test, or (in clean transect mode) any new frame that parses to a holdout transect, from seeding. A Refine round can never leak model-proposed labels onto the frozen gate it is being measured against.

**Gate meanings.** Each row in the rounds ledger (`rounds.csv`) carries three promotion-gate verdicts comparing that round against the current champion (or, if none is promoted yet, the best prior round). Since 2026-09-04 the gates are judged in the run's own metric family, recorded in the row's `metric_family` column: outline (mask) scores for a segmenter, box scores for a detector, so a detector's gates are real verdicts instead of blank passes:

- `gate_map`: pass if mAP50-95 in the run's family has not dropped more than 0.005 versus the baseline, else fail.
- `gate_class`: pass if no individual class's AP50-95 in the run's family (among classes actually present in train) dropped more than 0.05, else `flag:<codes>` naming the regressed classes.
- `gate_recall`: pass if recall in the run's family has not dropped more than 0.05 versus the baseline, else flag.

All three gates read **unpinned** whenever the dataset's split is not recorded and reproducible: no `split_manifest.json` exists, or the manifest records neither a transect holdout (`holdout_mode: "transect"`) nor a per-image pin table (`pinned` from the segmentation splitter, `pins` from the detection stager). A recorded split counts as frozen whatever its holdout mode, because the pins replay on every rebuild. All three read **incomparable** when the baseline was scored in the other metric family (a detector against an outline champion, or the reverse); a cross-family score is never ranked. Round-over-round comparison is only trustworthy on a frozen, leak-free holdout; an unrecorded split is honestly flagged as unmeasurable rather than shown as a false pass.

**Annotator single-instance rule.** The combined annotator is a single long-lived process per orchestrator instance. Launching Refine closes any Step-4 annotator that is already open before starting the loop-mode session, so exports always go to the project the operator intended and two annotator instances never race on the same `segmentations.json`.

## Edit Masks and canonical mask registry

Version 1.3.0 added a direct edit surface for masks a project has already exported, plus a permanent, cross-project canonical registry of every mask that every export upserts into.

**Edit Masks (sidebar tile, preferred port 5083).** The Edit Masks tile opens the standalone `TCRMPclip_editMasks` app against the current project's Step 4 export. It never creates a fresh export the way Step 4 (Place + Segment) or Refine can; it requires an existing `segmentations.json` to edit. Inside it, the operator can relabel a mask's species, delete a mask, redraw a mask's outline, or add a new mask to an already-processed frame, then export the changes. Masks carrying an accepted EXPERT-mode ID are locked against relabel and against any new REVIEW round-trip, so an outside expert's identification cannot be silently overwritten from the editor; a locked mutation is refused and the mask id is reported back rather than applied. An "unlabeled only" filter and a "next unlabeled" jump (`GET /api/unlabeled`) let the operator move directly through the backlog of masks that were exported without a species assigned, instead of paging through every frame by hand. Every edit action writes a `source: edit` row to `label_provenance.csv` (the shared `provenance.py` module, one copy per sub-tool, kept byte-identical) and upserts the mask's canonical registry row.

**Unlabeled-mask guard.** An unlabeled mask can no longer be accepted or exported anywhere in the pipeline. The combined annotator refuses to accept a mask with no species assigned, and the export path carries a matching backstop (`blocked_unlabeled` count in the export summary) so a mask that reached export some other way still cannot ship into `all_labels/` without a label. This closes the gap that produced the pre-1.3.0 backlog of masks exported with an empty species code.

**Canonical mask registry.** `scripts/_reefreview/mask_registry.py` defines `MaskRegistry`, writing `inprocess/_mask_registry/manifest.csv`: one row per content-stable `mask_uid`, across every project on the box. Every export upserts into it, whichever tool produced the export (the combined annotator, the standalone segment-images path, or Edit Masks), so the registry always reflects each mask's current species, category, review state, and source/project context, not just its state at first export. Concurrent writers are safe: upserts are serialized with a POSIX advisory lock so two pipeline steps writing at the same time cannot lose each other's rows. The label coverage matrix (`/matrix`) now derives its image x label grid from this registry rather than re-scanning raw per-project export state, with a fallback path preserved for masks recorded before the registry existed. See the [reef_point_seg_mask_registry](../../../_METADATA/dictionary/datasets/reef_point_seg_mask_registry.yaml) descriptor for the full field list, and [reef_point_seg_expert_id_library](../../../_METADATA/dictionary/datasets/reef_point_seg_expert_id_library.yaml) for the sibling permanent store that additionally keeps geometry sidecars for expert-reviewed masks.

**Coverage matrix drill-down, reviewer identity, preferences, composite exports, stats (2026-08-26).** Every matrix cell is clickable (Enter or Space from the keyboard) and opens a drawer showing the frame with that label's masks drawn on a canvas, one tab per project that annotated it, the linked projects (auto project name, run folder, who opened it, outcome, reviewer initials, timestamp) with "Open project folder" and "Copy path", and the mask-preference controls. Reviewer initials now travel with every mask: the orchestrator passes the initials of whoever opened the project (the launcher's access log) to each annotator launch as `TCRMP_REVIEWER` and re-posts them to a reused annotator (`POST /api/reviewer`), and they are stamped into `label_outcomes`, `label_provenance.csv`, `mask.reviewer`, and the registry's `reviewer` column; older rows read "unrecorded". "Use these masks" in the drawer writes `inprocess/_mask_registry/preferences.csv`; "Build composite export" on the matrix STATS tab assembles `inprocess/_composite/<name>/` from those choices (strongest-outcome fallback), and Step 6 offers it as a "Training source". The STATS tab also shows instances per species, stacked histograms by year and by site, images reviewed per year/site, masks per reviewer, and a registry-hygiene line with a purge action for test-residue rows (backup written first). `scripts/run_all_tests.sh` now redirects `TCRMP_MASK_REGISTRY_DIR` to a throwaway dir so test runs never write the live registry again.

**Reviewer identity is enforced, not just recorded (1.7.0).** Both annotator apps (the combined annotator and Edit Masks) now refuse any request that would create attributable work from a session carrying no initials: accepting a mask for the first time, relabeling a mask that is already accepted, `accept_all`, `commit_mask`, and every merge route when the merge's result would come out accepted. The refusal returns HTTP 200 with `{ok: false, needs_reviewer: true}` and applies nothing, so the client can prompt for initials in the top bar and retry; rejects, relabels of a still-pending mask, and an idempotent re-save of already-accepted work are exempt, so a frame save is never lost while the operator is entering initials. `TCRMP_REVIEWER` (the orchestrator's launch-time default, from the project's own access-log initials) now stamps the session before the annotator finishes opening, closing a gap where the first save or two of a session could go through before the stamp took effect.

**Coverage matrix in 1.6.0.** Four changes, all in `scripts/_matrix/`:

- **Merge, not replace.** Registry rows are now merged with each project's own ledger rows cell by cell, rather than a project's registry rows replacing its whole ledger. Work recorded only in a project ledger used to disappear the moment that project had any registry row at all: `run_18aprilpm` showed 5 records and now shows 1547. A project whose registry coverage is incomplete carries a "partially registered" badge so the count reads as a lower bound.
- **Third tab.** The matrix has three tabs: MATRIX (the grid), STATS (instances per species, masks by year and by site, images reviewed per year and per site, masks per reviewer), and TRAINING SETS. TRAINING SETS holds the composite exports list and the build form, with registry hygiene collapsed into a details block at the bottom.
- **Composite build form.** The form takes a name, your initials, the labels to export, a rebuild checkbox, and a mask-source choice: All sources, Hand-drawn only (`manual_box`, `manual_click`, `edit`), or Hand-drawn plus model-assisted accepted (the same three plus `model`). Rebuild replaces an existing composite in place with an atomic swap and keeps the previous build's metadata in `composite.json`'s history list.
- **Drawer.** The cell drawer gains "Open this project in the pipeline", which switches the orchestrator window to that project behind a confirmation, and an mtime-keyed cache that makes repeat drawer opens near-instant. The band and popover layering was corrected, and the dead "Found by model" legend state was removed.

## Annotate Images (standalone)

Version 1.4.0 moved bring-your-own-image annotation out of every project into its own launcher, so annotating a folder of photos no longer requires creating or opening a Reef Point Seg project.

**Launch (dashboard button, port 5096).** The VICARIUS launcher's Annotate Images button (`module.yaml` `ui.dashboards`, path `/annotate`) opens a small orchestrator page that starts the combined-annotator app in standalone mode on its own fixed port (5096, found free from there if occupied), polls until it is healthy, then redirects into the annotator. The orchestrator sets `TCRMP_SESSION_MODE=standalone`, `TCRMP_PROVENANCE_SOURCE=standalone`, and `TCRMP_STANDALONE_ROOT` (the module's `inprocess/_standalone/` directory); no project environment is set. Its runner key is `annotate`, separate from the project combined annotator's `step4test`/`step4loop` runner, so opening Annotate Images never closes or is closed by a project annotator session, and a standalone session in progress is never touched by `scripts/restart_reef_point_seg.sh`.

**Session setup.** The annotator boots into a single setup card: pick images (file picker, drop zone, or a server folder path), pick labels (a checklist of the master species codes plus a free-text "Other label"), and a session name that defaults to `<YY-MM-DD>_<initials>`. Starting the session creates `inprocess/_standalone/<session>/` and ingests the chosen images through the same `custom_imports` path a project's Import Images button uses (originals kept verbatim, delivered images downscaled to the 1920px lores standard when oversized, EXIF orientation baked in). The Import button used to bring outside images into a project session moves entirely to this standalone flow; project sessions (Step 4, Refine, Edit Masks) no longer show it.

**Review and export.** From there the session behaves exactly like a project annotator session: point and box prompts, review, refine, merge, exemplar scan. Export writes the same YOLO bundle a project export writes (`all_images/`, `all_labels/`, `export_manifest.csv`) into `inprocess/_standalone/<session>/`. See the [reef_point_seg_standalone_session](../../../_METADATA/dictionary/datasets/reef_point_seg_standalone_session.yaml) descriptor for the full session layout and `session.json` fields. Decision record [docs/adr/0006-annotate-images-exports-are-a-training-source.md](docs/adr/0006-annotate-images-exports-are-a-training-source.md) (2026-09-16) makes a session's export a Train Model training source beside the project export, the matrix training sets and the staged box datasets, without touching the coverage matrix or STATS; on 2026-09-17 the source list route `GET /api/composites` returns composites and box datasets only, so the session group is decided but not yet in the list. The same record corrects ADR 0001: a standalone session does not upsert into the mask registry (`src/app.py` answers "not found (standalone session)").

**Annotator work in 1.6.0.** Both annotator copies (combined annotator and Edit Masks) got the same batch. Saving is now safe: edits are flushed to disk on a debounce and Ctrl+S forces a save, each write goes through a temporary file and an atomic rename under a lock, and a torn-read negative control went from 533 bad reads to 0. Frame switching fetches the image and its mask data in parallel with a prefetch and an image cache, and the repaint waits for the data so a fast Next can no longer paint the previous frame's masks. SAM3 embedding warm-up runs in the background, so the first click on a frame pays only for the decoder. Mask JSON no longer carries the unused `rle` and `polygon_norm` fields, which shrinks every payload. The manual startup card was fixed, a scan-review keep failure no longer discards the candidates, Reload IDs and Merge same ID are wired again, the toolbar gained a Ref points checkbox, and both tools now use the single name "Annotate Images".

## Training, evaluation and inference in the main window

Since 2026-09-05 a model is trained, evaluated and run in one place: the VEGA main window (the orchestrator on port 5050), inside a project, on the Train Model, Evaluate Model and Model Inference stages (displayed as Steps 5, 6 and 7 on a segmentation project and Steps 1, 2 and 3 on a detection project; the step numbers below follow the segmentation rail). Nothing trains outside a project. A composite built on the coverage matrix or a box dataset staged on Bounding Boxes reaches training by minting a training project (see "Uniform training projects" below). The decision and its rejected alternatives are recorded in [docs/adr/0002-one-training-surface-the-vega-main-window.md](docs/adr/0002-one-training-surface-the-vega-main-window.md); the comparability rule is [docs/adr/0003-runs-compare-only-on-the-same-split-and-metric-family.md](docs/adr/0003-runs-compare-only-on-the-same-split-and-metric-family.md).

Historical note: a project-free page called Train + Infer at `/models` existed from 1.6.0 (2026-09-02) until 2026-09-05 and was retired because it forwarded no training task, no image size and four of about fifty training controls, seeded its detection split differently from the main window (so two scores shown side by side had been measured on different held-out images), and made every control exist twice (ADR 0002 above). Its page, script and stylesheet are gone; `scripts/_modellab/labruns.py` survives as the shared run library the orchestrator imports, and the lab folders it wrote under `inprocess/_models/` stay on disk and readable.

- **Train Model, "Starting model."** Since 2026-09-21 the Starting model select (`#s6-model`, renamed from Base model) lists base models only: one optgroup per task (YOLO11 nano to extra large, medium the default), plus a labelled YOLO26 optgroup kept because the recipe `config/presets/yolo26l_heavy_seg_aug.yaml` names YOLO26 weights and a recipe may only name weights the picker offers. A hint line under the select says a base model is what Ultralytics trained on COCO, a set of everyday photographs, and that VEGA teaches it the classes ticked in the training-data section above; a closed "What the model starts from" disclosure spells out the three terms VEGA uses for what a run starts from (base model, train from a base model, continue from a VEGA model), defined in [CONTEXT.md](CONTEXT.md). A second, closed "Continue from a VEGA model (advanced)" disclosure (`#s6-continue-details`) holds the earlier-run picker (`#s6-continue-from`: the champion first, then this project's runs, other projects, and runs trained outside a project, filtered to the training task), the Freeze layers field, and a note that choosing a run there sets Freeze layers to 10 and the learning rate to 0.001, restoring both when the choice is cleared; choosing a run there disables the Starting model select. The two former preset buttons ("Full retrain preset (recommended)" and "Fine-tune preset (fast loop)") and their routes (`/api/step/6/presets/finetune` and `/retrain`) are removed, because the form's default state (train from a base model) is the first and the disclosure (continue from a VEGA model) is the second. Decision record [docs/adr/0009-a-run-starts-from-a-base-model-and-continuing-from-a-vega-model-is-the-advanced-choice.md](docs/adr/0009-a-run-starts-from-a-base-model-and-continuing-from-a-vega-model-is-the-advanced-choice.md).
- **Evaluate Model, "All trained models."** Since 2026-09-21 the runs registry that used to sit on the Train panel lives on the Evaluate panel instead, behind a closed disclosure (`#s7-all-models`, summary "All trained models") that loads the table when it opens. It lists every run the module can see, project runs and lab runs alike (`GET /api/step/6/all_runs`), grouped by metric family ("Detectors, scored in box mAP50", "Segmenters, scored in outline mAP50"), the open project's rows marked "this project". Columns: State (champion, scored, not scored), Run (name never broken mid-token, with image size, mAP50-95 and the evaluation time in Atlantic Standard Time), Trained on (`trained_on` and `trained_on_kind` in the payload: the staged box dataset, the matrix training set or the project's own export the run learned from, read from `lab.json`, `project.json`, the split manifest or `provenance.json` and never guessed from a folder name; "not recorded" when no record exists), Score, Actions. Filters: Find a run, State, Source (This project, Other projects, Model labs) and Trained on, remembered per browser. Row actions: Evaluate (opens the Evaluate stage with that run selected), Promote (makes it the champion; disabled with its reason until the run has a ledger row), and Continue from (opens Train Model with that run chosen under Continue from a VEGA model; a cross-family choice is refused at the launch guard). A line above the table reads "Best so far: `<run>`, `<family>` mAP50-95 `<score>`, promoted `<stamp>`, the model Model Inference uses unless another is picked." Since 2026-09-17 the table presents no comparability: the "not comparable" chips and the comparability summary are gone from the screen, while `runs_comparable`, the split fingerprints and the gate verdicts stay in the payload and still gate promotion (decision record [docs/adr/0008-the-runs-table-names-training-data-and-drops-comparability-from-the-screen.md](docs/adr/0008-the-runs-table-names-training-data-and-drops-comparability-from-the-screen.md)). A Stop Training button sits beside Start Training on the Train panel while a run is live. Runs trained outside VEGA are listed once they are imported as a model lab; see "Detector training end to end" below.
- **Step 6, the report card ("Evaluation report").** Loads the newest evaluation of the run selected in the panel (`GET /api/step/7/report?run_dir=`), searching the project's `step7_evaluateModel/eval_*` folders and the module's `inprocess/_models/_eval/`: the run name and evaluation time, a Download PDF button (`GET /api/step/7/pdf`), a top line in the run's metric family, a per-species table with the full binomial in italics and the code as a chip, sortable by every column, where a species absent from the split reads "not present in this split", the precision-recall curves, both confusion matrices and the training curves (`GET /api/step/7/image`), the prediction samples, and the full report text behind a disclosure. A "Copy PDF to folder" control beside the card copies the PDF elsewhere. Evaluation image size is prefilled from the run's `args.yaml`; a blank field is filled by the server from the same file, and the panel says so.
- **Step 7, the gallery ("Inference results").** A run picker, newest first, over the project's `step8_inference/` runs and `inprocess/_models/_inference/` (`GET /api/step/8/runs`); a header with image and detection counts, the thresholds and image size the run used, and how many detections were skipped and why; one tile per image showing the overlay (or the raw frame, on a toggle) with one chip per detection reading the species in full, the code beside it and the confidence to two decimals; and Yes, No and Skip verdict buttons that append to `verifications.csv` in the run folder, stamped in Atlantic Standard Time (the last row per file wins). The panel has a device control (which GPU runs inference), and "Fill opacity" (formerly "Mask opacity") fills boxes as well as outlines, defaulting to 0.15 on a detector project so a full-frame box does not tint the whole image.
- **Correct numbers.** Before 2026-09-04 the evaluator indexed the per-species arrays by raw class id, while Ultralytics orders them by the classes present in the split (`ap_class_index`); on the Coral Intel detector 39 of 55 rows carried another species' scores and the last four species were dropped. Rows now follow `ap_class_index`, absent classes are listed under `absent_classes`, instance counts come from the validator's own tally, five-field detection labels are parsed so ground truth draws in the previews, and the metric family is chosen from the numbers and used in the report, the ledger and the gates. A run evaluated before the fix has no `metrics_schema` value in its ledger row; re-evaluating it rewrites the row.
- **Comparable runs.** Two runs may be ranked against each other only when their metric family and their split fingerprint match (`runs_comparable` in `scripts/_modellab/labruns.py`); both splitters seed the detection split on the staged dataset name, so the same dataset splits the same way wherever it is trained, and a staged dataset carrying its own `split_pins.json` has that split replayed before any draw, so an imported model and a VEGA retrain hold out the same images (holdout mode `staged`, decision record [docs/adr/0004-staged-datasets-carry-their-split-pins.md](docs/adr/0004-staged-datasets-carry-their-split-pins.md)); a run without a recorded fingerprint is never comparable. A gate verdict across families records `incomparable`. None of this is rendered on the runs table any more (ADR 0008 above); it acts in the promote route's 409 response and in the ledger's gates.
- **Champion.** Promote (`POST /api/step/7/promote`) writes one family-aware record (`run_dir`, `promoted_at`, `metric_family`, `map50_95_M` or `map50_95_B`, `note`) twice: beside the run's own ledger, where the evaluator reads its gate baseline, and at `inprocess/_models/champion.json`, which Model Inference and the Continue from a VEGA model disclosure read. It is the model Model Inference uses unless another is picked, and the first choice under Continue from a VEGA model; it is not what a run starts from unless it is chosen there. Records in either of the two earlier shapes are still read.
- **Evaluate scores the run that was picked.** A run of the open project is scored on the project's dataset, writes its report to `step7_evaluateModel/eval_<run name>/` and appends its row to the project's `rounds.csv`, as it always has. A run the project does not own (a run in a model lab, or another project's run) is scored on its own dataset, writes its report to `inprocess/_models/_eval/<run name>_<stamp>/` where the report card already looks for it, and appends its row to that owner's ledger, so the runs card shows its score. Nothing of that run reaches the open project: its Evaluate step keeps the status, the completion stamp and the output pointers it had before the launch, and the status poll carries one sentence saying whose run finished. A run reached through a path outside the module's `inprocess/` folder, by `..` or by a symlink, is refused.
- **Which training recipe a project opens with.** Two controls on the Train panel decide it: Training task (Segmentation or Detector) and Subject (coral, fish, algae or other). Every recipe in `config/presets/` declares the pair it was written for in its `_meta` block (`task:` and `subject:`), the dropdown lists only the recipes matching both controls, and exactly one match is selected and applied the first time a project's Train step is opened, never again once that project's saved configuration carries a recipe (a hand-tuned project is not overwritten on reload). Two matches apply nothing: the panel names both and the operator picks, because a tie broken by file name is how a coral recipe would have taken the fish detector's place in silence. No match applies nothing and says so. A recipe declaring neither key is listed as unclassified and is never selected on its own. A staged box dataset can record its own `subject` in `ingest_manifest.json`, which sets where the Subject control starts and nothing else.
- **Full names on every class.** A staged dataset's `names.csv` is copied into the split dataset's `data.yaml` as `names_full`, and the evaluator, the inference overlay and the Step 6 report card read it from there, so a class token such as `EPST_Normal` is always shown with the name behind it (Epinephelus striatus, Nassau grouper, normal phase). `metrics.json` records the same mapping under `class_full_names`. A TCRMP class keeps resolving through the master codes table as before.
- **Safety.** A second Start Training while a run is live is refused with HTTP 409 before any file is written (it used to rebuild, and so delete, the box dataset the live trainer was reading); the refusal leaves the live run's status untouched; a trainer that outlived an orchestrator restart is found by its process and named in the refusal. Warnings a run route returns (a detector note, an image-size mismatch, an auto-filled value) render in the panel. On a box-dataset project the split controls that cannot act (minimum samples, pinned split) are hidden, the validation and test fractions reach the stager, and the Training task is pinned to Detector.

## Uniform training projects

Version 1.7.0 made "train on what the matrix or Bounding Boxes already assembled" a one-click action that mints an ordinary pipeline project, so a training run gets the same Step 6 (augmentation, learning rate, loss weights, starting model, evaluate, promote, infer) that a from-scratch project gets, instead of a second, thinner training surface.

- **Two mint points, one minter.** The matrix Training Sets tab's "Create training project" button (`POST /matrix/api/composite/create-project`, `{name, by}`) mints from a composite; the Bounding Boxes page's "Train in VEGA" button (`POST /boxes/api/create-project`, `{dataset, by, reuse}`) mints from a staged box dataset, or reuses the newest project already minted for that dataset, and opens it in the main window (`/?project_dir=<encoded run dir>`, window name `reefpointseg_orchestrator`). Both call the same `mint_training_project` (`scripts/_reefreview/training_projects.py`), so the run-dir naming (`run_{YY-MM-DD}_{INITIALS}_train_{source-name}`), the skipped-step bookkeeping, and the atomic `project.json` write are identical; only the source-specific block differs (`project.json.composite` vs `project.json.training_source`). See the [reef_point_seg_training_project](../../../_METADATA/dictionary/datasets/reef_point_seg_training_project.yaml) descriptor for the full field list.
- **Skips steps 1-4.** A training project's `project.json` writes steps 1 through 4 as `status: "skipped"` and opens on Step 6 (`current_step: 6`); a project already progressed past Train on a later reopen keeps its saved step instead of being forced back. A composite-sourced project gets a relative `step4test_combinedAnnotate` symlink into the composite, so Train reads `all_images/`, `all_labels/`, and `data.yaml` with no image copied; a box-sourced project holds no imagery at all and Step 6 builds its own split by reading the staged dataset's recorded path directly, keeping the module's non-TCRMP scope rule intact.
- **Training task selector.** Step 6 gains a "Training task" control inside its existing "Advanced hyperparameters" disclosure: Segmentation (default, selected) or Detector (boxes only), forwarded to the trainer as `TCRMP_STEP6_TASK`. A composite-sourced project can train either task, since its polygons reduce cleanly to boxes (`scripts/TCRMPtrain_oceankindCV/src/detect_dataset.py::build_detect_from_seg_dataset`); a box-sourced project defaults to detect, since raw boxes carry no outline to learn from. The Starting model select swaps to the matching weight family (`yolo11{n,s,m,l,x}-seg.pt` versus `yolo11{n,s,m,l,x}.pt`) when the task changes; every other Step 6 control applies to both tasks unchanged. The control is deliberately unstyled, so segmentation stays the obvious default and detector stays a considered choice, not a shortcut. On a box-dataset project the control is pinned to Detector, and the two split controls that cannot act on a staged dataset (minimum samples per class and the pinned transect split, both belonging to the outline splitter) are hidden; the validation and test fractions apply, since the stager takes them from the panel and records them in the split manifest.
- **Project cards.** The VICARIUS launcher's project card for a training project carries a badge naming its kind and source, and counts masks, images, and species straight from the project's own annotation store when one exists (falling back to the export ledger only when it does not), the same store-first rule every project card now follows.

## Bounding Boxes

The Bounding Boxes page (`/boxes`, a launcher dashboard button and a Tools sidebar link; hiding both behind admin mode is open TODO `T20260903-154500`) stages box-annotated datasets from outside TCRMP, converts boxes to outlines, and hands training to the main window. Its code is `scripts/_boxes/`. It trains nothing itself, and it draws nothing: boxes are imported from a prepared YOLO dataset, and VEGA has no box-drawing tool. To change the boxes, change them where the dataset was made and stage it again.

- **Scope rule.** Non-TCRMP imagery never enters `inprocess/run_*`, the mask registry, the coverage matrix, or STATS. The page states this at the top and the exclusion is enforced in code, not by convention.
- **Two stagers.** Both write `supporting_data/bbox_datasets/<name>/` in one layout: `images/`, `labels/`, `data.yaml`, `classes.txt`, `LICENSE.md` and `ingest_manifest.json`. The Coral Intel stager (`scripts/_boxes/ingest_coral_intel.py`, the page's own button) reads that one distribution, derives its class map from the file names and adds `labels_localized/`; re-running it copies only what changed. The generic YOLO stager (`scripts/_boxes/ingest_yolo_boxes.py`, run from a terminal) stages any YOLO box dataset: an images folder, a labels folder holding one `class cx cy w h` text file per image, and a class list given as a `data.yaml` or a token-to-name table. It normalises every basename on the way in (a name with spaces, a non-ascii character or a `.jfif` extension is not a name the trainer reads back), records every rename in `rename_map.csv`, and adds two optional files the training side honours: `names.csv`, the full name behind every class token, and `split_pins.json`, the split the dataset's original experiment used. Nothing is staged until every check passes; a basename collision, a label line that is not five fields, a class id outside the class list, a label with no image, a class token with no full name, a pin for an image that is not there, or a destination already holding files the run would not write each stop the run with a message naming the fault.
- **What is staged.** Six datasets, all under `supporting_data/bbox_datasets/`. Coral Intel (`coral_intel`): 10361 images, 14247 boxes, 59 species, of which 1278 are whole-frame boxes (1272 by the exact-form count; both numbers are in the manifest). A whole-frame box says only that the species is somewhere in the picture, so conversion skips them unless the operator ticks "Include whole-frame boxes". Fish photo 28 Feb 25 (`fish_photo_28feb25`), staged 2026-09-15 by the generic stager: 7572 images, 14130 boxes, 34 species and colour-phase classes, 321 background images (a staged image whose label file holds no box, which shows a detector what a frame with nothing to find looks like), a names table for all 34 classes, and split pins for all 7572 images (train 5300, valid 1514, test 758). The remaining four are offline-augmented or trimmed variants of Coral Intel plus a small practice set: `coral_intel_subset` (8348 images, 11995 boxes, 32 species), `coral_intel_t2aug` (24875 images, 34070 boxes, 59 species, augmented and split the way the source paper describes), `coral_intel_t2aug_leaky` (31083 images, 42700 boxes, 59 species, built from `config/augment_presets/coral_intel_table2_leaky.yaml`; this set lets the same photograph appear in training and in test at once, on purpose, to measure how far that overlap inflates scores, so it is never a set to select or report a model from) and `tutorial_boxes` (400 images, 511 boxes, 4 species, for practice). Every dataset's exact counts are in its own `ingest_manifest.json` and on its card (below).
- **Dataset cards.** Each card reads the dataset's own `ingest_manifest.json` and folder and shows what is there: images, boxes, classes, whole-frame boxes, background images, how many class tokens its names table names, which stager wrote it, and the per-split pin counts in the order train, valid, test. A count the stager never wrote reads "none recorded" rather than zero, a zero is shown as the fact it is, and a pins file the server could not read reads "unreadable", which is also what stops a training project built on it. The folder a dataset was staged from is deliberately not shown: every manifest on this box records a path through somebody's personal tree. A dataset the page cannot restage itself carries the line naming the stager that writes it again.
- **License.** The Coral Intel annotations and the dataset-level arrangement are CC BY 4.0, copyright 2026 Elvin Cordero. Cite Cordero, E., Sherman, C. E., Yadav, P., Raju, V. K., Townsend, J. E., and Courtney, T. A. (2026), "Coral Intel: a YOLOv8 deep learning framework for monitoring Caribbean corals", Intelligent Marine Technology and Systems 4, Article 18, https://doi.org/10.1007/s44295-026-00107-5. The photographs in `images/` are third-party, sourced from GBIF, CoralNet, and Corals of the World, and are explicitly excluded from that grant: each remains governed by its own source record. Treat them as local training material only; do not republish or redistribute them. The full notice ships at `supporting_data/bbox_datasets/coral_intel/LICENSE.md`. A dataset staged without terms or a citation shows "none recorded" on its card and never borrows Coral Intel's: `fish_photo_28feb25` reads that way, and its `LICENSE.md` says local training only until the terms are recorded.
- **Train in VEGA (primary action, section 2 of the page).** Picking a staged dataset and pressing Train in VEGA posts initials to `POST /boxes/api/create-project`, which mints a `run_*` project (`project_type: bbox_training`) with the dataset as its recorded source, or reuses the newest project already minted for it, and opens that project in the main window on Step 5 Train Model; nothing is copied into the run dir. The page lists the training projects a dataset already has (`GET /boxes/api/training-projects`). This is the paved road from any staged dataset to a detector. See "Uniform training projects" above and "Detector training end to end" below.
- **Boxes to masks (behind a disclosure).** SAM3 turns each box into an outline and writes a YOLO segmentation dataset to `inprocess/_bbox/<name>/`; nobody has reviewed these outlines, so they are a training starting point rather than reviewed labels. The job takes the same GPU the annotator uses, and there is no cross-page lock, so do not convert while someone is segmenting. The in-page quick trainer that used to sit here was retired with the project-free training page on 2026-09-05; the image size for a Coral Intel detector (its frames are 256x256) is set on Step 5 of the training project, where the platform default is 512.
- **Detector weights.** The detection base weights `yolo11n.pt`, `yolo11s.pt`, and `yolo11m.pt` are staged locally under `supporting_data/model_weights/` and `scripts/TCRMPtrain_oceankindCV/`, so a detector run needs no download. `yolo11l.pt`, the base model the fish preset names, has sat beside the trainer at `scripts/TCRMPtrain_oceankindCV/yolo11l.pt` since 2026-09-14 23:57 AST. The x detect variant is still not staged.

## Detector training end to end

A detector trained on imagery from outside TCRMP follows the same Train, Evaluate and Inference steps every VEGA model follows; staging replaces the four steps that collect and annotate TCRMP frames. The whole path, in order:

1. **Stage the dataset.** Coral Intel has its own button on the Bounding Boxes page. Any other YOLO box dataset is staged from a terminal with the generic stager, which prints its counts and writes nothing until every check passes:

   ```
   cd /mnt/rip/vicarius_drive/vicarius/modules/reef_point_seg/github_repo
   env/bin/python scripts/_boxes/ingest_yolo_boxes.py \
       --images <source>/all_images --labels <source>/all_labels \
       --data-yaml <source>/data.yaml \
       --names scripts/_boxes/names/<dataset>.csv \
       --split-from <source>/split --name <staged name>
   ```

2. **Give the classes their full names.** `--names` takes a two-column table, header `token,name`, one row per class token. The stager writes it into the staged folder as `names.csv`, the split builder copies it into the split dataset's `data.yaml` as `names_full`, and the evaluation report, the inference overlay and the Step 6 report card read it from there. The tables live in `scripts/_boxes/names/`; the fish one is `scripts/_boxes/names/fish_photo_28feb25.csv`. A class token with no row stops the run rather than being staged nameless.
3. **Keep the dataset's own split.** `--split-from` points at a folder holding `train/`, `valid/` and `test/`, each with an `images/` folder inside; the stager records which split each image was in as `split_pins.json`, keyed by the staged basename. The split builder replays those pins before any seeded draw, so a model trained elsewhere on this dataset and a retrain here hold out the same images. Without `--split-from` the dataset is split by the seeded draw exactly as before. The rule and its alternatives are recorded in [docs/adr/0004-staged-datasets-carry-their-split-pins.md](docs/adr/0004-staged-datasets-carry-their-split-pins.md).
4. **Import the runs the dataset already has (optional).** Finished ultralytics detection runs trained outside VEGA become one model lab, so the runs card lists them, Evaluate scores them and Promote can make one of them champion:

   ```
   env/bin/python scripts/_boxes/import_external_runs.py \
       --dataset supporting_data/bbox_datasets/<staged name> \
       --lab <lab name> --note "<where these runs came from>" \
       --runs <experiment>/training_runs/<run> [<run> ...]
   ```

   The importer copies each run's `weights/best.pt`, `args.yaml` and `results.csv` with a `provenance.json` naming its source, and rebuilds the lab's `dataset/` on the staged split pins. It writes no ledger row and no champion record: a score reaches the ledger only from an evaluation VEGA measured itself. Any failure after the lab folder is claimed removes the whole folder, so a half-written lab never survives.
5. **Mint the training project.** On the Bounding Boxes page, pick the dataset, type your initials and press Train in VEGA. VEGA mints a `bbox_training` project (or reuses the newest one for that dataset) and opens it in the main window on Train Model. No imagery is copied into the run directory; Step 6 reads the staged folder where it is.
6. **Train.** Two controls on the Train panel decide the recipe: Training task, pinned to Detector on a box-dataset project, and Subject, which starts on whatever the staged dataset recorded as its `subject` (`fish` for `fish_photo_28feb25`, `coral` for `coral_intel` and `coral_intel_subset`) and can be changed to coral, fish, algae or other at any time. The Load preset list shows only the recipes written for that pair, and the first time the step is opened VICARIUS fills the form from the single match: `config/presets/fish_heavy_augment_640.yaml` for detector plus fish, 36 fields of the October 2025 fish ablation's run3 recipe (mosaic 1.0, mixup 0.15, copy-paste 0.1, rotation 15, scale 0.5, hue 0.3, yolo11l at 640 px, batch 32), and `config/presets/coral_heavy_augment_640.yaml` for detector plus coral, 35 fields of the recipe approved for the Coral Intel subset (mosaic 0.6, mixup 0.12, no copy-paste, rotation 12, scale 0.6, hue 0.1, the same base model and image size). Two recipes written for one pair fill nothing: the line under the picker names both and the operator picks, which is why a coral recipe can sit beside the fish one without taking its place. No match fills nothing and says so. Change anything before pressing Start Training; once the project has a saved configuration, no later open overwrites it.
7. **Evaluate and compare.** Pick any run on the runs card and press Evaluate. A run the project owns is scored into its own Step 7 folder; a lab run is scored on the lab's dataset, written to `inprocess/_models/_eval/<run name>_<stamp>/` and added to the lab's ledger, and the open project's Evaluate step is left as it was. Two runs may be ranked against each other only when their metric family and their split fingerprint match, which is what the replayed pins secure.

**The fish detector, 2026-09-15.** The dataset was staged as `fish_photo_28feb25`: 7572 images, 14130 boxes, 34 species and colour-phase classes, 321 background images, one name disambiguated for letter case, and all 7572 images pinned (train 5300, valid 1514, test 758). Its six paper runs were imported as the lab `fish_photo_28feb25_paper`, whose dataset carries split fingerprint `f4f9263d8334e606` and holdout mode `staged`. The training project `run_26-09-15_LO_train_fish_photo_28feb25` auto-applied the fish preset and trained one smoke epoch whose `args.yaml` carries the run3 augmentation exactly; its own dataset carries the same fingerprint, so the imported runs and anything trained in that project are comparable. Evaluating `run3_heavy_augment` from the project scored box mAP50 0.9008 and mAP50-95 0.8259 into `inprocess/_models/_eval/run3_heavy_augment_20260915_024311/` with a 10-page PDF, put the row in the lab's `rounds.csv`, and left the project's Evaluate step pending. The 0.9008 is the same model that scored 0.9042 where it was trained: that experiment ran ultralytics 8.3.222 and this module runs 8.4.38, which returns identical precision and recall and integrates average precision differently. ### Staged names must be unique ignoring letter case

This whole tree sits inside a Synology Drive sync whose destination cannot hold two file names that differ only in case. At 01:26 AST on 2026-09-15 the sync found `labels/Nurse_shark.txt` and `labels/nurse_shark.txt` in a freshly staged dataset and renamed the second to `nurse_shark_vicar-mainframe_Sep-15-012645-2026_CaseConflict.txt`, four minutes after the stager wrote it. The image that label described was left with no label, so the dataset held one labelled pair fewer than its manifest counted, and every split fingerprint computed from it changed.

The stager therefore makes every staged name unique ignoring case. Two source names that reduce to one staged name are still refused, because there an operator has to look at the source; two that differ only in case are both real files, so the later one in sorted source order takes a numbered suffix on its stem (`_2`, then `_3`), its label file follows the stem, `rename_map.csv` records it like any other rename, and `ingest_manifest.json` counts it under `n_case_disambiguated`. In `fish_photo_28feb25` that count is 1: `nurse shark.png` was staged as `nurse_shark_2.png` beside `Nurse shark.JPG` staged as `Nurse_shark.jpg`. The rule covers the staged dataset folder itself, which may not match a sibling dataset folder in the same staging root only by case, and a suffix that would push a name past the file-name length limit stops the run while it is still planning.

If a file carrying `CaseConflict` in its name ever appears under `supporting_data/bbox_datasets/` or `inprocess/_models/`, the sync resolved a clash that reached disk before this rule did. Count the dataset's images and labels and check that they still pair (`ls <dataset>/images | wc -l` against `ls <dataset>/labels | wc -l`, 7572 each for `fish_photo_28feb25`), then stage the dataset again rather than renaming by hand, because a dataset whose pairs no longer match trains and scores on a set its manifest does not describe.

## Expert-review flagging is suspended

Since 2026-09-06 no annotator will set a new REVIEW flag on a mask (Lauren Olinger's ruling). This section says exactly what that means and how to reverse it.

**What still works.** Every mask flagged before that date keeps its flag, its reviewer identifier and its review history, and still reads back as flagged everywhere: the annotators, the mask registry, the coverage matrix and the exports. Importing an expert identification still works and still returns a mask to training. Reading, displaying, filtering and merging an existing flag are all unchanged.

**What is refused.** Any request that would create a new flag, on any route in any of the four applications (Place plus Segment, Annotate Images, Edit Masks, Segment Images), is refused with HTTP 409 and the message "Flagging for expert review is temporarily unavailable. VICARIUS is accepting no new review tags." The refusal happens before any segmentation runs, so nothing is written and then cleaned up: the frame is left exactly as it was. The tag has four spellings in the stored data, and all four are refused, in any capitalisation, with surrounding whitespace, and with zero-width characters mixed in:

| Spelling | Where it appears |
|---|---|
| the `review` key set to a true value | the mask record |
| `species` set to REVIEW | the mask record |
| `species_code` set to REVIEW | the mask record |
| `category` set to "Review" | the mask record, reachable through the relabel route |

A label that merely contains those letters is not affected: REVIEWED and PREVIEW are ordinary labels and pass through. A mask carrying a real species beside a Review category keeps its species and loses only the category.

**On screen.** The REVIEW button is still in place, greyed out, reading "temporarily unavailable", with a tooltip that says flagging is suspended and that masks flagged before 2026-09-06 are unchanged. The R keyboard shortcut no longer arms it. The REVIEW chip in the category picker is greyed the same way. Nothing was removed, so the control comes straight back when the switch is flipped.

**Publishing is suspended too.** `POST /api/export_review_bundle` used to mint a fresh review identifier onto every already-flagged mask and push the bundle to the expert-review repository. It now returns without publishing and reports how many masks it skipped.

**Environment labels.** A REVIEW entry in `TCRMP_TARGET_SPECIES` is dropped at startup rather than offered as a label, so a hand-set environment cannot put the control back.

**Reversing it.** Set `REVIEW_TAGGING_ENABLED` to true in `scripts/TCRMPclip_combinedAnnotate/src/mask_ops.py`, in its byte-identical twin `scripts/TCRMPclip_editMasks/src/mask_ops.py`, in the copy at `scripts/TCRMPclip_segmentImages/src/mask_ops.py`, and in `scripts/TCRMPclip_placePoints/src/export.py`. No markup needs editing: every button reads its disabled state, its tooltip and its help text from that one constant, so the control returns on its own. Note that `scripts/TCRMPclip_combinedAnnotate/src/mask_ops.py` and its Edit Masks twin are held byte-identical by `TCRMPclip_combinedAnnotate/tests/test_shared_file_parity.py`, so both must change together or the board goes red.

**Tests.** Seven suites cover the lock: `TCRMPclip_combinedAnnotate/tests/test_review_lock_core.py`, `test_review_lock_routes.py`, `test_review_lock_ui.py` and `test_target_only_shows_pending.py`; `TCRMPclip_editMasks/tests/test_review_lock_routes.py`; `TCRMPclip_segmentImages/tests/test_review_lock_routes.py`; and `TCRMPclip_placePoints/tests/test_review_lock_points.py`.

## Gotchas and troubleshooting

- **This box's two GPUs are shared, and the orchestrator checks with VICARIUS before it starts a stage that needs one.** The Place + Segment annotator needs two CUDA GPUs (see "SAM3" above), and Step 6 Train Model can take one or more. For a missing PDF, check that `/usr/bin/google-chrome` exists or point `TCRMP_CHROME_BINARY` at another Chrome, and open the evaluation folder's `report.html` in a browser to see what Chrome was asked to print.
- `scripts/_matrix`, `scripts/_labels`, `scripts/_reefreview`, `scripts/_expertids` and the combined annotator's `src/app.py` (`scripts/TCRMPclip_combinedAnnotate/src/app.py`) are tracked in git; only their `__pycache__` folders are not. The orchestrator kills any running annotator before launching a fresh one so exports go to the active project; if exports appear in the wrong project, a stale annotator process was still bound.
- The combined annotator excludes REVIEW-flagged masks from the YOLO training set even when a reviewer accepted them. They routed to the expert-review bundle instead and re-enter training only after the operator imports an expert ID. Since 2026-09-06 no new mask can be flagged, so this applies only to the masks flagged before that date; the exclusion itself is unchanged, and importing an expert identification still returns a mask to training.

A save writes only when something changed, and never over a `segmentations.json` that changed on disk since the process last read or wrote it: it writes `segmentations.conflict-<stamp>.json` beside it and the page shows "Not saved" in red. The orchestrator and both restart scripts ask a live annotator to save (`POST /api/flush`) before stopping it; that part takes effect only after the orchestrator restarts. SIGKILL cannot be caught, so anything that sends it must save first.
- `scripts/snapshot_runs.py` copies `inprocess/` (run folders and shared stores, trained weights excluded) to `/mnt/tear/vega_run_snapshots/daily/<stamp>/` from cron at 02:30, hard-linking unchanged files and keeping the newest 14. The log is `/mnt/tear/vega_run_snapshots/daily/snapshot.log`.
- The CPCe point lookup (`TCRMPclip_placePoints/src/app.py`, `find_cpc_rows_any_season`) searches every season folder of `cpc_all`, previous season first, because frames surveyed from January to June 2018 are filed under 2017. Before 2026-09-27 routing dropped them.
- No frame is screened twice for the same label (since 2026-09-27). Before Step 3 the orchestrator writes `step3_chooseImages/prior_screening_input.json` from `scripts/_reefreview/screening.py` (built on the coverage matrix cells, other projects only), and `select_images.py --prior-screening` drops frames screened elsewhere for every target label from both the selection and the reserve. Before every annotator launch it writes `step4test_combinedAnnotate/prior_screening.json`; the annotator shows those masks as locked previews and records no `not_found` for a label screened elsewhere. Previews never enter `segmentations.json`, exports or the registry. Both writes need the orchestrator restarted to take effect, and a failure to write either is logged and never blocks the step.
- Blank species codes surface as real training classes (empty name in `class_map.json`). Known, flagged for review. `--save_crops` on `run_inference.py` is accepted and ignored (recorded under `ignored_flags` in the manifest) and is no longer offered by the panel.
