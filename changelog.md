# Changelog

## 2026-07-14 15:05 AST - Closing the launch window now cancels the routing pass; routing is visible and stoppable (LO)
- Operator requirement: these tools are only ever launched from the web UI, so work that keeps running after the window is closed has no way to be seen or stopped. It also caused real damage: an abandoned routing pass held the GPU and, on finishing, killed a live annotator to launch one nobody was waiting for (the 14:30 entry above).
- Cancelling is cheap, which is what makes cancel-on-close the right default: placePoints flushes `detections.json` every 50 frames and its `/api/configure` skips frames it already has (outcome `already_processed`), so reopening RESUMES and only redoes the handful of frames since the last flush. It never re-OCRs the whole selection.
- `scripts/pipeline_orchestrator/app.py`: added a `route_cancel` Event. `_route_drive` polls it between every step of the pass (health wait, OCR loop, export, flatten) and, critically, immediately before the annotator launch - so a pass that was abandoned after routing completed can no longer kill a live annotator and spring a new one. Cancelling kills the routing sub-app at once (that is what holds the GPU). New `POST /api/step/step4test/cancel`; `POST /api/step/step4test/stop` now stops BOTH the annotator and any routing pass (a Stop that leaves the GPU pegged is not a stop). Neither clobbers a `ui_ready`/`idle` phase.
- `scripts/pipeline_orchestrator/static/orchestrator.js`: closing the launch popup now CANCELS (routing) or STOPS (a SAM3 load in progress) instead of only abandoning the browser poll. The popup itself is now a live region - it showed a frozen "this can take up to a minute" for the entire pass while the real progress bar ticked in the main tab behind it, so a 6-minute route looked hung; it now shows frames done/total, a bar, and honest timing (~1 image/sec).
- `scripts/pipeline_orchestrator/templates/index.html`: new tile banner (`s4test-route-banner`) that surfaces an in-flight routing pass with progress and a `Stop Routing` button (tooltipped, per house rule). It is driven off `route_status`, so it survives closing the launch window AND a full page reload: background work can no longer be invisible. Overlay `Close` relabelled `Hide` with a tooltip saying the launch keeps running and where to stop it.
- `scripts/pipeline_orchestrator/tests/test_step4test_route_cancel.py` (new, registered in `run_all_tests.sh`): cancel kills the routing stage and marks the pass cancelled; Stop kills annotator AND routing; cancel does not clobber a good phase; the tail refuses to launch an annotator when cancelled; a fresh pass clears a stale cancel.
- Tests: full `run_all_tests.sh` 70/70 green. Verified live: orchestrator restarted, `POST /cancel` returns 200 and leaves an idle phase untouched, banner markup and cancel wiring served to the browser.

## 2026-07-14 14:30 AST - "Combined Annotator did not become ready (port 5080)": in-flight routing race fixed (LO)
- Root cause: an in-flight ROUTING pass was reported to the browser as a ready ANNOTATOR on a stale port. `_run_step4test` launches routing under runner key `step4test_route`; when a pass from an earlier click was still driving (closing the launch popup abandons the frontend poll but NOT the background thread), `run_flask_stage` returned "Step step4test_route is already running", and `/api/step/step4test/run` matched the bare substring "already running" - a branch written for the ANNOTATOR key - and answered `phase:"ui_ready"` with `runner.ports["step4test"]`, a port whose process was long dead. The UI then polled that dead port for its whole deadline and gave up. Confirmed from the 2026-07-14 logs: 237 status polls at 500ms from 13:50:40 to exactly 13:52:40 (the 120s deadline) with ZERO health probes ever reaching 5080, while the stale thread's annotator finished loading SAM3 at 13:52:44, four seconds too late.
- `scripts/pipeline_orchestrator/app.py`: `_run_step4test` now returns the live routing phase when a pass is in flight (the UI attaches to `route_status` and shows progress instead of waiting on a port nobody is serving); the `/run` "already running" branch is narrowed to the annotator key (`step4test`), which cannot match `step4test_route`; a stranded routing stage with no live driver is now reclaimed via `runner.kill` rather than failing every Open click; and `_route_drive`'s tail no longer launches an annotator when the project changed mid-route (it received `project_ctx` and never read it, so a route for project A would bind an annotator to project B's empty routed_input - which is exactly what put a bogus annotator on 5080 at 13:52:37).
- `scripts/pipeline_orchestrator/static/orchestrator.js`: the three launch waiters (Combined Annotator, Refine Review, Edit Masks) now wait on the PROCESS rather than a fixed 120s clock - a cold SAM3 load outlives any fixed deadline. They poll while the process is alive (10-min ceiling, matching the server's own SAM3 ceiling) and fail fast with a distinct message when nothing is running behind the port.
- `scripts/pipeline_orchestrator/tests/test_step4test_route_inflight.py` (new, registered in `run_all_tests.sh`): reproduces the incident (live route thread + stale port -> must not report ui_ready), guards the legitimate live-annotator ui_ready branch, and pins the changed-project tail guard.
- `scripts/pipeline_orchestrator/tests/test_editmasks_routes.py`: SEPARATE PRE-EXISTING HAZARD found while verifying the above - running the house test suite KILLED whatever annotator was live on the box. Every launch route reaches `_kill_all_annotators()`, which does not confine itself to the runner's processes: it `pkill -f`s both annotator entry scripts and `fuser -k`s ports 5080-5089. `test_run_already_running_reuses_port` stubbed `run_flask_stage` but not `subprocess.run`, so it reached the real pkill/fuser. `subprocess.run` is now neutered for that whole module (as the other launch-path suites already do). A decoy-process sweep over all 66 python suites confirms none of them can now kill a live annotator, and the full suite was re-run against a live annotator on 5080 which survived it. Anyone adding an orchestrator test that touches a launch route MUST stub `subprocess.run`.
- Tests: full `run_all_tests.sh` 69/69 green. Verified end-to-end on the live box: orchestrator restarted, project reopened, Open launched a healthy annotator on 5080 bound to the correct project + completed routed_input.

## 2026-07-01 02:37 AST — Fix: "Open Combined Annotator" does nothing (popup silently blocked)
- ROOT CAUSE (two compounding): (1) `_launch_step4test_ui` unconditionally kills + relaunches the annotator on EVERY open (the 2026-06-30 export-binding fix), so even when it was already up for the same project, each click forced a ~1 min SAM3 reload and drifted its port off 5080 (find_free_port races on the just-freed port). (2) The frontend called `window.open()` only AFTER that ~60s await chain, so the browser's popup blocker killed it — outside any user activation — and there was no `if(!win)` fallback, so Open appeared to do nothing. Other steps opened fine because they reuse a running service, firing window.open within the activation window.
- FIX 1 (backend, `app.py`): new `_annotator_reusable(routed_dir)` — reuse the running annotator (no kill/relaunch) ONLY when it is healthy AND bound to the CURRENT project id + input dir. Preserves the 2026-06-30 wrong-project-export invariant (mismatch still kills + relaunches) but restores the instant same-project fast path. `step4test_state` now tracks `project_id`/`input_dir`; cleared on stop/reset.
- FIX 2 (frontend, `orchestrator.js`): open the popup synchronously inside the `openStep4test` click handler (`openStep4testPlaceholder`, shows a loading page), then NAVIGATE that same window to the annotator once healthy — never a fresh `window.open()` from an async callback. Blocked-popup and closed-popup cases now surface a message instead of failing silently.
- Verified: second `/run` reuses the same PID+port (5080) instantly, no relaunch/port-drift; annotator serves 200 at the navigate URL. Tests: orchestrator UI suite 26/26 (new `test_step4test_popup_opens_on_user_gesture` guard); step4test clipdir/route/flatten green.
