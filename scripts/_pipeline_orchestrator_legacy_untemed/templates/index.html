Step 1: Make All Points

What this does: Parses ~839 TCRMP Coral Video Review (CVR) Excel workbooks spanning 2001–2025 into a single unified CSV dataset. Each row represents one benthic point observation (species ID at a specific frame/transect/site/date). This is the foundation dataset for all downstream steps.

Produces: all_points.csv (~2.3M rows), master_codes.csv (~130 species codes), and a parse_log.txt.

Runtime: ~2–5 minutes depending on disk speed.

Step 2: Recode Species

What this does: Coral taxonomy has changed over the years (e.g., Montastraea → Orbicella). This step applies species code remappings so that old and new names map to a single consistent code. You can also exclude ambiguous codes from top-10 coral ranking.

Produces: all_points_recoded.csv, master_codes_recoded.csv, and remap_log.json (audit trail).

Step 3: Choose Images

What this does: Selects a balanced set of video still frames for building a training dataset. Frames are chosen so that each target coral species is equally represented across years, sites, and transects. This prevents temporal, spatial, or species bias in the final dataset.

Key settings: Choose which species to target, how many frame-instances per species, and the year range. More instances = larger dataset but longer processing downstream.

Produces: selected_frames.csv (master list), route files for CPC vs OCR processing, diagnostic plots.

Step 4: Route Chosen Images (OCR)

What this does: Takes selected frames and extracts exact (x,y) pixel coordinates for each benthic point annotation. Pre-2020 frames use existing CPC point coordinates. Post-2020 frames are processed through a GPU-accelerated OCR pipeline that detects letter labels (A–T) and crosshair markers in annotated images.

Interactive: Opens a review UI where you can verify and correct point detections, then export verified data in SAM3-compatible format. Process batches, review, and export iteratively.

Requires: NVIDIA GPU (CUDA) for OCR processing.

Step 5: Segment Images (SAM3)

What this does: Uses Meta's Segment Anything Model 3 (SAM3) to generate pixel-level instance segmentation masks for each coral colony. Each verified point click from Step 4 becomes a SAM3 prompt. The model segments the coral at that point, producing a polygon mask.

Interactive: Opens a review UI where you can accept/reject masks, refine boundaries with additional clicks, merge overlapping masks, and scan for similar colonies. Export produces YOLO-format labels for training object detection models.

Requires: Dual NVIDIA GPUs (CUDA) — one for point prompts, one for exemplar scanning.

Step 6: Train Segmentation Model

What this does: Takes the YOLO-format segmentation dataset exported by Step 5 (all_images/ + all_labels/ + data.yaml), splits it into train/valid/test using stratified sampling, then trains an Ultralytics YOLO segmentation model.

Runtime: Training is long — tens of minutes to hours depending on dataset size, epochs, imgsz, and GPU. You can close the orchestrator and come back; logs are persisted.

Outputs: {step6_dir}/dataset/ (splits) and {step6_dir}/runs/<run_name>/ (weights, plots, metrics).

Time-impact legend below each field: ★ free (bounds/naming, no compute cost)   ★★ minor (small CPU/GPU overhead)   ★★★ major (linearly or quadratically scales wall time).

Unit: string. Names the run folder under runs/. Blank → auto-stamped <project_name>_YYYYMMDD_HHMMSS.
Size n→x = ~4× more params, ~4× wall time. For ~hundreds of frames, m is the sweet spot. YOLO26 is newer/better in theory but has open ONNX/TensorRT export bugs as of 2026-04.
Unit: integer count of passes over the training set. Linear time impact. Use patience (below) to early-stop — effective epochs are usually far fewer.
Unit: pixels (square). GPU memory grows as imgsz² ; time per epoch roughly doubles when you double imgsz. 512 is a good default for coral quadrats; 640–1024 only if fine-grained boundaries matter.
Unit: images per GPU step. -1 lets ultralytics auto-size to fit GPU memory. Larger = faster per epoch but more memory. Very small (<4) can destabilize training.
DDP note: multi-GPU training (Device = 0,1) does not support -1 — set an explicit batch size that's a multiple of your GPU count (e.g. 16 for 2 GPUs).
Unit: fraction in [0, 0.9]. Portion of labeled frames held out for val-set metrics each epoch. 0.15–0.25 is typical.
Unit: fraction in [0, 0.9]. Held out entirely from training; used for final generalization check. 0 disables test-split; fine for small datasets.
Unit: integer. Classes with fewer than this many labeled instances fall back to random (non-stratified) split. Raise for balanced reporting; lower for sparse datasets.
Unit: integer epochs. Training stops if val metric doesn't improve for this many epochs. Lower = shorter real runtime but risk stopping before convergence. 30–100 typical.
DDP = Distributed Data Parallel — PyTorch's native multi-GPU training mode. Ultralytics turns it on automatically when you pass a comma-separated device (e.g. 0,1). Each GPU holds a copy of the model, each step's batch is split across the GPUs, and gradients are all-reduced between GPUs via NCCL every step so the replicas stay in sync.

When it helps: larger models (l / x), higher imgsz (≥ 640), and datasets in the thousands of frames — per-step compute dominates the inter-GPU sync, giving ~1.7–1.9× speedup on 2 GPUs.
When it doesn't: small datasets / small models / small imgsz — the all-reduce overhead can eat most of the gain (speedup 1.0–1.3×), and per-epoch behavior gets harder to reason about (validation runs on rank 0 only; effective batch doubles unless you halve batch).

Alternative: pick Single GPU — cuda:1 for this run so the other GPU is free to run a second independent experiment in parallel — that's guaranteed 2× throughput across experiments.

Color & image quality (HSV jitter — helpful for underwater variation)
Each value is the max ± fraction of jitter applied randomly per image during training. ★★ minor CPU overhead; no impact on epochs needed.
Geometric augmentation
Apply random geometric transforms per image. ★★ minor CPU overhead. Over-strong settings (big rotation, shear, perspective) on tiny masks can actually hurt — defaults are conservative.
Sample mixing (seg-specific tricks to amplify rare classes)
Each P is the probability of applying the mixing augmentation to a given image. ★★ minor CPU overhead. Copy-paste is the big lever for segmentation with long-tailed coral classes.
Optimizer & LR schedule
★ free runtime cost — these change learning dynamics, not wall time per epoch. Bad values can, however, stall training and effectively waste epochs.
Loss weights — scale contributions of each loss term
★ free. Relative weights only matter as a ratio; their absolute scale is absorbed by LR. Defaults are ultralytics' tuned-for-general-use values.

Step 7: Evaluate Model

What this does: Runs Ultralytics val on a chosen training run against the held-out test split from Step 6, then assembles an educational report with every metric defined in plain English, a per-class breakdown, sample overlay imagery, and the training curves from the run.

Outputs: report.md, metrics.json, report.pdf, and a previews/ folder with rendered sample predictions, all inside {step7_dir}/eval_<run>/. You can also export a copy of the PDF to any folder you choose.

Good defaults for 95% of cases — split=test, imgsz auto-read from the chosen run's args.yaml (fallback 1024), conf=0.25, iou=0.6, preview_count=8. Only tweak if you specifically need to.

Step 8: Model Inference

What this does: Runs a trained model over new frames and saves overlay renderings + a manifest of predictions. Pick one of four sources:

  • Directory — any folder of .jpg/.png images.
  • Unused TCRMP frames — random or systematic sample of images in TCRMP_clip/ that are NOT in this project's Step 3 selected_frames.csv. Great for finding blind spots in the training set.
  • Full TCRMP image set — every raw frame under TCRMP_clip/.
