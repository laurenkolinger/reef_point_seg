Step 1: Fetch Points

Step 1 makes the point dataset every later step reads: all_points.csv, one row per benthic point annotation, plus master_codes.csv, the label-code lookup. Without it there are no points to balance, place, or segment.

Do this: paste the paths to an existing all_points.csv and master_codes.csv from a previous run and press Fetch Points. Build from raw workbooks only when no such CSV exists yet, under "Make points from scratch".

What happens: Fetch Points symlinks the two CSVs into this project with no re-parsing. Make points from scratch parses about 839 raw CVR Excel workbooks (2001–2025) into a fresh all_points.csv (about 2.3M point rows) and master_codes.csv (about 130 label codes), which takes 2 to 5 minutes.

Next: Step 2 reads all_points.csv and master_codes.csv to recode the label codes.

Background: why this step exists

The TCRMP reef monitoring program records benthic point counts from video transects. Each survey is stored as an Excel CVR (Coral Visual Record) workbook, about 839 of them spanning 2001 to 2025, one workbook per survey. A workbook holds the per-frame, per-transect label code at each point (20 points, A to T, per frame). The workbooks use three different layouts across the years, so the points live in spreadsheets that downstream code cannot read directly. This step parses every workbook into one flat table, all_points.csv (about 2.3M point rows), and aggregates the per-code lookup into master_codes.csv (about 130 label codes), so the rest of the pipeline works from CSV instead of Excel.

Fetch Points (default)

Paste the paths to an all_points.csv and master_codes.csv from a previous run. We symlink them so downstream steps use them with no re-parsing. This is the usual path.

Make points from scratch (run occasionally)

Only needed when no all_points.csv exists yet. Parses the raw CVR Excel workbooks (about 2 to 5 min).

Step 2: Fetch Labels

Step 2 collapses the historical label codes onto one consistent code per organism, so a species counted under several old codes is counted once. This is what makes downstream label counts and the trained classes coherent.

Do this: Browse to a remap_log.json from a previous recode and press Load Labels, or open the recode UI to build a new remap.

What happens: the remap is applied to Step 1's all_points.csv (about 2.3M point rows), reassigning renamed codes (for example Montastraea → Orbicella) onto one code and writing all_points_recoded.csv, master_codes_recoded.csv, and remap_log.json as an audit trail.

Next: Step 3 reads master_codes_recoded.csv to build the target-label list and all_points_recoded.csv to count frames per label.

Background: why this step exists

Coral taxonomy was revised over the 2001 to 2025 survey span, so the same organism appears under several historical codes. For example the Montastraea genus was reclassified to Orbicella in 2012, and the older workbooks kept the old codes while newer ones used the new codes. The makeAllPoints parse in Step 1 preserves every code as written in its source workbook, so all_points.csv still carries those drifted codes side by side. If they were left split, one species would be scattered across multiple labels and its point count would read low. Step 2 applies a remap that reassigns each old code to one current code and records every change in remap_log.json, so the recoded dataset has one code per organism and the change is auditable.

Step 3: Choose Images

Step 3 builds a balanced training set of video still frames. It chooses frames so each label you target is represented evenly across years, sites, and transects, which stops the model from learning a year or a site instead of the species.

Do this: pick the labels to target below, set how many frame-instances you want per label, and set the year range, then run the selection.

What happens: the selector reads the recoded points from Step 2 (all_points_recoded.csv) and chooses frames toward your per-label target, writing selected_frames.csv plus the CPC and OCR route files and diagnostic plots.

Next: Step 4 reads selected_frames.csv to pull the exact point coordinates for each frame.

Why a label sometimes does not reach its target

The selector counts one instance per frame that contains a label, not per point. It keeps pulling frames for a label until the target is met or it runs out of frames that contain that label. A label can finish below target for reasons that are about the data, not a fault in the selection:

  • Not enough frames exist. A rare label may appear in fewer frames than the target, so every available frame is taken and the count still falls short.
  • Year range. Min Year and Max Year shrink the pool. A label common only outside that window will be scarce inside it.
  • Pre-2020 frames without point coordinates. Older frames are kept only when their CPC point coordinates are on file; frames missing those coordinates are dropped before selection, which lowers the available count for labels concentrated in early years.

When a label finishes short, the selection log reports it as short and states how many frames actually exist for it.

Step 4: Place Points

Step 4 fixes the exact (x,y) pixel location of each benthic point in every selected frame, which is what SAM3 needs as a click to segment the right colony. It exports those verified points in SAM3-compatible format.

Do this: open the Place Points review UI, work through each batch verifying and correcting the detected points, then export each batch.

What happens: the review UI loads the frames in selected_frames.csv from Step 3. Pre-2020 frames reuse their existing CPC point coordinates; post-2020 frames run through a GPU OCR pass that reads the letter labels (A–T) and crosshair markers in the annotated images. Export writes the verified point coordinates per frame.

Next: Step 5 reads the exported points and uses each as a SAM3 prompt to segment the colony at that location.

Requires: NVIDIA GPU (CUDA) for the OCR pass.

Step 5: Segment Images (SAM3)

Step 5 turns each verified point into a per-colony segmentation mask, the pixel outlines a detector trains on. It exports those masks as YOLO-format labels.

Do this: open the SAM3 review UI, then per batch accept or reject masks, refine boundaries with extra clicks, merge overlapping masks, and export.

What happens: each verified point from Step 4 becomes a SAM3 prompt; Meta's Segment Anything Model 3 segments the colony at that point into a polygon mask. Export writes YOLO-format label files (all_images/, all_labels/, data.yaml).

Next: Step 6 reads all_images/, all_labels/, and data.yaml to train the segmentation model.

Requires: dual NVIDIA GPUs (CUDA), one for point prompts and one for exemplar scanning.

Step 6: Train Segmentation Model

Step 6 trains the YOLO segmentation model that does the actual coral detection. Its weights are the deliverable the later steps evaluate and run.

Do this: name the run (or leave it blank for an auto-stamped name), pick the base model, epochs, image size, and device, then start training.

What happens: the trainer reads the YOLO-format dataset from Step 5 (all_images/, all_labels/, data.yaml), splits it into train/valid/test by stratified sampling, then trains an Ultralytics YOLO segmentation model. Training runs tens of minutes to hours depending on dataset size, epochs, imgsz, and GPU; logs persist, so you can close the orchestrator and come back. Outputs land in {step6_dir}/dataset/ (splits) and {step6_dir}/runs/<run_name>/ (weights, plots, metrics).

Next: Step 7 reads runs/<run_name>/weights/best.pt to evaluate the trained model on the held-out test split.

Unit: fraction in [0, 0.9]. Portion of labeled frames held out for val-set metrics each epoch. 0.15–0.25 is typical.
Unit: fraction in [0, 0.9]. Held out entirely from training; used for final generalization check. 0 disables test-split; fine for small datasets.
Unit: integer. Classes with fewer than this many labeled instances fall back to random (non-stratified) split. Raise for balanced reporting; lower for sparse datasets.
Unit: integer epochs. Training stops if val metric doesn't improve for this many epochs. Lower = shorter real runtime but risk stopping before convergence. 30–100 typical.
DDP = Distributed Data Parallel — PyTorch's native multi-GPU training mode. Ultralytics turns it on automatically when you pass a comma-separated device (e.g. 0,1). Each GPU holds a copy of the model, each step's batch is split across the GPUs, and gradients are all-reduced between GPUs via NCCL every step so the replicas stay in sync.

When it helps: larger models (l / x), higher imgsz (≥ 640), and datasets in the thousands of frames — per-step compute dominates the inter-GPU sync, giving ~1.7–1.9× speedup on 2 GPUs.
When it doesn't: small datasets / small models / small imgsz — the all-reduce overhead can eat most of the gain (speedup 1.0–1.3×), and per-epoch behavior gets harder to reason about (validation runs on rank 0 only; effective batch doubles unless you halve batch).

Alternative: pick Single GPU — cuda:1 for this run so the other GPU is free to run a second independent experiment in parallel — that's guaranteed 2× throughput across experiments.

Step 7: Evaluate Model

Step 7 measures how well the trained model performs on frames it never saw during training, so you can judge whether it is good enough to run. It assembles a report you can read and share.

Do this: pick a completed Step 6 training run, keep the split on test, and run the evaluation (or press Use recommended defaults first).

What happens: Ultralytics val runs the chosen run against the held-out test split from Step 6, then the report is built with each metric defined in plain English, a per-class breakdown, sample overlay imagery, and the run's training curves. Outputs are report.md, metrics.json, report.pdf, and a previews/ folder, all under {step7_dir}/eval_<run>/; you can also copy the PDF to a folder you choose.

Next: Step 8 reads the same run's weights/best.pt to run inference on new frames.

Good defaults for 95% of cases — split=test, imgsz auto-read from the chosen run's args.yaml (fallback 1024), conf=0.25, iou=0.6, preview_count=8. Only tweak if you specifically need to.

Step 8: Model Inference

Step 8 runs the trained model over new frames it was never trained on, so you can see how it behaves on real unseen data and find where it struggles. It saves overlay renderings and a manifest of predictions.

Do this: pick the trained run, choose a source of frames, and run inference. Sources:

  • Directory — any folder of .jpg/.png images.
  • Unused TCRMP frames — random or systematic sample of images in TCRMP_clip/ that are NOT in this project's Step 3 selected_frames.csv. Useful for finding blind spots in the training set.
  • Full TCRMP image set — every raw frame under TCRMP_clip/.

What happens: the model runs over the chosen frames using weights/best.pt from the selected Step 6 run, writing overlay images and a prediction manifest to the output folder, then a gallery renders below. You can tag each frame yes / no / skip to flag where the model is struggling, a verdict only, no mask editing.
